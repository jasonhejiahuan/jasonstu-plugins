# AI prompt: create or extend PPQ Base v1

Produce UTF-8 compact JSONL for PPQ Base v1, one record per line, without Markdown fences, indentation or explanatory text. Read `docs/ppq-base.md` and `docs/examples/valid-minimal.jsonl` first.

Use the provided original question paper and its exact matching mark scheme as the source of truth. Preserve original question wording, necessary context, diagrams, subpart numbers, original marks, emphasis, mathematical notation, explicit line breaks and examiner `Accept` / `Do not accept` instructions. Put the original mark-scheme excerpt in `mark_scheme.raw`; normalized study notes must not replace it. Never invent a source, asset digest, difficulty, absent question text or examiner policy.

Write one bank record first with `schema:"ppq-base/1"`. Declare shared source metadata once per paper, then reference it by ID. Use stable descriptive IDs and positive integer revisions. Emit source/asset records supplied by the caller verbatim unless the task explicitly requests a verified correction. Attachments are separate files under `assets/`, referenced by ID, with SHA-256 provided by the extraction tooling; never print Base64. If the question needs an unavailable diagram or source, report the missing input before producing an importable bank.

New packages require bank `provenance:{version:1,origin,verification,creator:{name,model},packagedBy:{name,model},packagedAt}` as defined in `docs/ppq-base.md`. Credit the original resource creator separately from the packaging agent. Record declared/known model names exactly, or `null` if unknown; do not substitute the packaging model for the author's model. Preserve supplied attribution and all metadata. Use `third-party` for externally supplied material and `unverified` until original source review actually occurs. A successful format check never establishes source verification. Apply author fallback names only when explicitly supplied by the user for this batch. Use the actual packaging time with a timezone.

Before creating a new card, compare supplied existing originals. Merge only a source-verified match in original task, wording, necessary context/assets and marks; do not merge merely because answers or topics resemble one another. For a verified duplicate, keep its stable ID and primary source/mark_scheme/modes, append the new source ID to `source` (convert a string to an ordered array when needed), and put the new paper’s exact `part`, `marks`, `location:{qpPage,msPage}`, `markSchemeRaw` and supplied provenance in `sourceDetails[newSourceId]`. Keep existing primary source first. Declare each source record only once. Preserve published revisions and create a new revision for added provenance. Do not blend different MS wording or drop Accept/Do not accept rules. Different marks require separate cards. If uncertain, flag the candidate for review instead of merging it.

Provide an independent short-answer mode and only those single-choice, keyword-multi-select or cloze assistance modes that faithfully exercise the original mark points. Give every mode a unique ID and label. Keep assistance prompts, options, accepted blank answers and scoring mappings separate from `stem`. Map marks explicitly; do not assume that every selected correct word earns a mark. Make capped “any N” mark_schemes explicit. When a cloze or single-choice scaffold uses one full-credit pathway, set `pointScope` to its unique mark-point IDs, include all prerequisite IDs, and map only those points. Preserve the complete original `mark_scheme` and all alternative points. Set `manual:true` with notes for semantic judgement that cannot be captured reliably by literal rules.

Copy every supplied core or extension field recursively, preserving JSON types and array order, including metadata this version does not understand. Do not replace unknown fields with a summary. Exact large integers and high-precision decimals must be strings. Use ordinary Unicode and escape embedded newlines as `\n`; do not expand Unicode to `\uXXXX` unnecessarily. Never emit duplicate keys or duplicate IDs/revisions.

Reuse chapter labels already supplied for the same source subject, board, code and qualification, including across banks. The app automatically groups matching chapters from active banks without rewriting imported records. Keep identically named chapters from different subjects, qualifications or exam systems separate; never combine them using the chapter text alone. Add a new readable `chapter` only when the supplied classification calls for it. Omit the field if unknown.

Rough practice levels, when explicitly supplied or supported by the requested source, use `difficulty.level` equal to `confidence`, `balanced` or `challenging`, with a non-empty `difficulty.basis`. Manual assignments may use the basis `User-assigned rough level`. These labels do not change marks or scoring rules; never infer one from the mark total or automatically rate an unrated question. Omit difficulty for Unrated. Preserve an existing arbitrary difficulty level and every nested extension exactly if the task does not explicitly change it; do not convert unknown levels into a guessed rough level or silently delete them.

If updating an existing question, keep its stable ID and use `max(existing rev for that ID) + 1`; retain supplied historical revisions and do not replace an already published revision. The app presents the greatest revision per question ID while keeping earlier content for history. Preserve extraction provenance and record changes in extension metadata. A review status must describe verification actually performed, including paper variant and page references; do not label automatically extracted content “verified.” A classification-only edit does not change the original wording or its source-verification status.

For diagram short answers, retain the original diagram as a separate raster attachment and insert `![descriptive alternative text](asset:asset-id)` in its correct `context` or `stem` position. Use the existing `short` mode; preserve labels, axes, units, captions and authored line breaks. Keep paired asset `width` / `height` as the actual positive integer pixel dimensions when supplied. Record crop provenance in `meta.diagrams:[{assetId,qpPage,crop:[x0,y0,x1,y1],units:"pt",pdfSha256}]`, using one-based pages and top-left PDF point coordinates, plus supplied extraction metadata. Do not invent a hash, re-create a diagram or output Base64; the extraction tool supplies the attachment and measured values.

For the current non-calculation diagram collection, add `meta.questionType:"diagram-short-answer"`, `meta.requiresCalculation:false` and `meta.reviewStatus:"pending-user-review"` until source checking actually occurs. Include only independent textual responses: exclude numerical calculations, numerical graph readings, parts requiring a previous calculated answer, drawing, sketching and diagram annotation. A mixed question's qualitative subpart may be retained with its complete necessary context. Judge the required response and MS, not the mere presence of numbers. Preserve the exact same-variant MS and mark any judgement beyond reliable literal matching as `manual:true`; do not invent keyword rules to make an extracted question look automatically graded.

Before returning, validate mark caps, point dependencies, source and asset references, mode IDs, option IDs and accepted-answer mappings. Unknown metadata must survive. Return only complete compact JSONL records. If required information is missing, explain the missing information instead of fabricating an apparently valid record.

Question prose must remain selectable rich text: place each original figure between the surrounding text blocks, keeping authored line breaks, emphasis, subscripts and superscripts. Crop only the original figure, internal labels and caption; never use a raster screenshot as the question stem or context paragraph. Source-backed manual transcription resolves undecoded text. Original MS row evidence may remain a separate image, with extracted marking text retained in `mark_scheme.sourceText`.
